## Què hi ha en aquesta guia

Documentació oficial: [wiki.nftables.org](https://wiki.nftables.org)

- Punt de partida: el servidor ja reparteix adreces per la targeta interna.
- Les regles viuen a `/etc/nftables.conf` i les carrega el servei `nftables`.

## Per què no fem servir iptables

Tota la documentació d'Internet parla d'`iptables`, amb comandes com `iptables -t nat -A POSTROUTING -o enp1s0 -j MASQUERADE`. Encara funcionen, però és una capa de compatibilitat: per sota, avui, hi ha `nftables`.

`nftables` és el sistema de tallafoc de Linux des de fa anys i el que trobaràs a qualsevol servidor nou. Té una sintaxi unificada i les regles es desen en un fitxer que pots llegir i versionar.

**No barregis els dos.** Si escrius regles amb `iptables` i les consultes amb `nft list ruleset` les veuràs traduïdes, i al revés no. Tria un i queda-t'hi.

## Una regla mal escrita et tanca la porta

<Callout kind="recordatori">

Estàs escrivint un tallafoc. Si poses `policy drop` a la cadena `input` sense permetre SSH, perdràs la connexió en carregar les regles. En aquesta pràctica deixem `input` amb `policy accept` justament per evitar-ho: filtrem el trànsit que _travessa_ el servidor, no el que hi arriba.

</Callout>

## Anàlisi del fitxer de configuració

Les regles viuen a `/etc/nftables.conf`. Té dues taules: `filter` decideix què pot passar i `nat` canvia les adreces.

### Les cadenes que no filtren

```text title="input i output"
chain input {
    type filter hook input priority 0;
    policy accept;
}
chain output {
    type filter hook output priority 0;
    policy accept;
}
```

- `input` és el trànsit que arriba al servidor i `output`, el que en surt. Tots dos queden oberts: filtrem el trànsit que _travessa_ el servidor.

### El trànsit que travessa el servidor

```text title="forward"
chain forward {
    type filter hook forward priority 0;
    policy drop;

    # de la xarxa interna cap a Internet
    iifname "enp2s0" oifname "enp1s0" accept

    # només les respostes de tornada
    iifname "enp1s0" oifname "enp2s0" ct state related,established accept
}
```

- `policy drop`: el que no està permès, no passa.
- La primera regla deixa sortir la xarxa interna cap a Internet; la segona només deixa tornar les respostes.
- `iifname` i `oifname` comparen el nom de la targeta: les regles es poden carregar encara que la targeta no hagi aparegut durant l'arrencada.

### El NAT

```text title="postrouting"
table ip nat {
    chain postrouting {
        type nat hook postrouting priority 100;
        # NAT a la targeta que surt a Internet
        oifname "enp1s0" masquerade
    }
}
```

- `masquerade` canvia l'adreça d'origen dels clients per la de la targeta externa del servidor.

## El fitxer complet

És el fitxer sencer amb els tres trossos anteriors. Canvia els noms de les targetes pels teus.

<details class="fold">
<summary>Mostra el fitxer complet</summary>

```text title="Regles · nftables"
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
    chain input {
        type filter hook input priority 0;
        policy accept;
    }
    chain forward {
        type filter hook forward priority 0;
        policy drop;

        # de la xarxa interna cap a Internet
        iifname "enp2s0" oifname "enp1s0" accept

        # només les respostes de tornada
        iifname "enp1s0" oifname "enp2s0" ct state related,established accept
    }
    chain output {
        type filter hook output priority 0;
        policy accept;
    }
}

table ip nat {
    chain postrouting {
        type nat hook postrouting priority 100;
        # NAT a la targeta que surt a Internet
        oifname "enp1s0" masquerade
    }
}
```

## Convertir el servidor en porta d'enllaç

1. **Mira com està ara** l'encaminament:

   ```bash title="Terminal"
   cat /proc/sys/net/ipv4/ip_forward
   ```

   Sortirà `0`.

2. **Activa'l de manera permanent** amb un fitxer propi, que és més net que tocar el fitxer general:

   ```bash title="Terminal"
   echo "net.ipv4.ip_forward=1" | sudo tee /etc/sysctl.d/99-encaminament.conf
   sudo sysctl --system
   ```

   Torna a comprovar-ho: ara ha de sortir `1`. I sobreviurà a un reinici.

3. **Escriu les regles**, enganxa-hi el fitxer complet i canvia els noms de les targetes:

   ```bash title="Terminal"
   sudo nano /etc/nftables.conf
   ```

4. **Comprova la sintaxi** sense aplicar res:

   ```bash title="Terminal"
   sudo nft -c -f /etc/nftables.conf
   ```

5. **Activa el servei** perquè carregui les regles ara i a cada arrencada:

   ```bash title="Terminal"
   sudo systemctl enable --now nftables
   ```

   <Callout kind="nota">

   **Compte** `enable --now` fa les dues coses alhora. No facis `enable & start` amb un sol `&`: això envia la primera comanda a segon pla i sembla que funciona quan no ho ha fet.

   </Callout>

6. **Comprova que les regles s'han carregat:**

   ```bash title="Terminal"
   sudo nft list ruleset
   ```

   Hi han de sortir les regles del fitxer, amb la regla `masquerade` a la taula de NAT. Si surt buit, comprova `systemctl status nftables` i `sudo journalctl -u nftables` per trobar l'error.

<Callout kind="nota">

**Ubuntu 26.04** Al `nft list ruleset` les prioritats no surten com les has escrit: on tu poses `priority 0` hi llegiràs `priority filter`, i on poses `priority 100`, `priority srcnat`. Són els noms dels mateixos números: la regla s'ha carregat bé.

</Callout>

## Comprovar que els clients surten a Internet

Prova-ho des del client, per capes, en aquest ordre:

```bash title="Terminal"
ip route              # la porta d'enllaç és el servidor?
ping -c3 192.168.1.1  # arribo al servidor?
ping -c3 9.9.9.9      # surto a Internet?
ping -c3 www.upc.edu  # funciona el DNS?
```

La gràcia és l'ordre: la primera que falli et diu exactament on és el problema. Si la IP va i el nom no, comprova si el nom es resol abans de concloure que falla DNS.

## Publicar cap a fora un servei de la xarxa interna

`dnat to` reescriu l'adreça (i el port, si cal) de destinació d'un paquet abans que el nucli decideixi cap a on l'encamina. Per això viu al ganxo `prerouting`, amb la prioritat `dstnat`. Canviar la destinació no obre pas tot sol: amb `policy drop` a `forward`, cal una regla que ho permeti.

1. **Afegeix una cadena `prerouting`** dins la taula `ip nat` que ja tens, abans de `chain postrouting`:

   ```text title="Regles · nftables"
   chain prerouting {
       type nat hook prerouting priority dstnat;
       # trànsit extern cap al servidor intern, port 80
       iifname "enp1s0" tcp dport 80 dnat to 192.168.1.10:80
   }
   ```

2. **Permet que aquest trànsit travessi el `forward`**, dins la taula `inet filter`, abans de la regla de `ct state related,established`. El dnat ja ha canviat la destinació, així que el port que es mira és el **del servidor intern**:

   ```text title="Regles · nftables"
   iifname "enp1s0" oifname "enp2s0" tcp dport 80 accept
   ```

3. **Valida i recarrega:**

   ```bash title="Terminal"
   sudo nft -c -f /etc/nftables.conf
   sudo systemctl restart nftables
   ```

4. **Comprova-ho des de fora**, des d'un client de `puigcastellar1`:

   ```bash title="Terminal"
   ip -brief a          # al servidor, la IP externa
   curl http://IP-EXTERNA-DEL-SERVIDOR/
   ```

   Ha de respondre el servei que corre a `192.168.1.10`, tot i que el client només coneix l'adreça externa del servidor.

## Criteris professionals

<Callout kind="bones pràctiques">

- **`policy drop` a `forward`** i obre només el que cal. El que no s'ha permès, no passa.
- **Fes servir `ct state related,established`** per al trànsit de tornada, en lloc d'obrir el sentit contrari sencer.
- **Configuració permanent, no de sessió.** Un `sysctl -w` o un `nft add rule` desapareixen en reiniciar.
- **Activa NAT només a la targeta externa.** Un `masquerade` a la interna amaga qui és qui i complica qualsevol diagnòstic.
- **Prova per capes** (ruta → servidor → IP externa → nom) abans de tocar res.

</Callout>
